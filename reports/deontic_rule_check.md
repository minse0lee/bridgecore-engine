# Deontic 범주 대응 규칙 점검 (2026-11-03)

규칙: `bridgecore/deontic_rule.py` — 가이드라인 7절 조동사 표를 코드로 옮김. 원문 범주(의무·권고·허가·금지·의무 없음)와 번역 범주를 비교해
범주가 뒤집힌 경우(flip)와 뜻이 분명한 규범 표지가 번역에서 사라진 경우(vanished)를 표시한다. 판정은 하지 않고 LLM 힌트로만 넣는다
(`prompts/v1_2` = v1.1 시스템 프롬프트 그대로 + `rules.json`으로 이 힌트만 켬. v1.1 해시는 바뀌지 않음).

## 1. 파일럿 개발용 40문항
- 규칙이 걸린 문항 2개(P053 금지→의무 없음, P057 mandates 표지 사라짐) 모두 정답 Deontic 훼손. 오경보 0
- 정답 Deontic 훼손 3칸 중 P045는 조건(절단 위치) 변화라 규칙 대상이 아님
- 그런데 v1.1은 P053·P057을 이미 모든 실행(Sonnet 2회, Haiku 2회, 2단계)에서 맞힘. v1.1의 Deontic 오류(P039·P056 오탐, P045 놓침)는 규칙이 다루지 않는 유형
- → 개발용에서 규칙으로 바뀔 칸이 없음. 개발용 재실행은 하지 않음 (힌트가 붙는 문항이 이미 맞힌 2문항뿐)

## 결론
- 드러난 범주 뒤집힘은 v1.1이 규칙 없이도 Haiku까지 모두 잡는다. 규칙 힌트를 더해도 측정되는 이득이 없다
- 규칙만으로 판정하면 재현율 0.63 (주체·조건·범위 변화를 못 봄) → **Deontic은 LLM 판정 유지** (계획서의 '규칙/LLM 배분은 성능 비교로 결정'에 대한 결과)
- v1.2는 채택하지 않고 v1.1 유지. 규칙 코드와 합성 세트는 남겨 둠 (본검수 결과 분석 때 규칙 단독 성능 비교용)

## 한계
- 합성 세트는 Claude가 만든 문장을 Claude가 판정한 것이고, 뒤집힘이 실제 오류보다 노골적이라 쉬운 시험이다. 만점은 '이 유형은 이미 해결됨'의 근거일 뿐 엔진 전체 성능이 아니다
- 문항당 1회 실행이라 0.97과 1.00의 차이는 의미 없다
